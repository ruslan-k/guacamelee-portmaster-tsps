# Max color attachment and resolve blocker

## Root cause fixed in diagnostic source

With `LIBGL_NOTEST=1`, `GetHardwareExtensions()` returns from the notest branch before the normal draw-buffer capability fallback. `hardext.maxcolorattach` therefore stayed zero.

The color texture attachment validation rejected every color attachment:

```text
VALIDATE ... attachment=0x8ce0 maxcolorattach=0
```

Correct source change for the notest branch:

```c
hardext.maxdrawbuffers = 1;
hardext.maxcolorattach = 1;
```

With `hardext.maxcolorattach=1` and `hardext.depthstencil=1`:

The remaining issue is upstream of SDL present: the source path feeding FBO1/FBO2 contains black pixels despite successful draw calls. The next trace must sample source FBO1 immediately before each resolve and identify which logical FBO receives the actual scene draw. No presenter workaround is promoted because it was proven to copy a black texture.
