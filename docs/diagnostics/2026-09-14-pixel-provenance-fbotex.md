# Pixel provenance and FBO2 transition diagnostic

Date: 2026-09-14
Target: TrimUI Smart Pro / Spruce

## Result

This run separates the controller prompt from the later black title state.

At swap 10, the clean coherent gl4es build produced the same real image in all three stages:

```text
app   fb=1  hash=675ae5fc56b53803  nonblack=2080/6144
 game fb=1  hash=675ae5fc56b53803  nonblack=2080/6144
window fb=0  hash=fe3ab3a5c020a0bf  nonblack=2016/6144
```

A full readback confirms that the image is not noise or a vignette. It is the actual game prompt:

```text
Controller Recommended
```

The physical KMS capture taken immediately after the same swap-10 PPM dump shows the identical controller prompt. Therefore:

```text
GL render -> game_fbo -> window framebuffer -> SDL_GL_SwapWindow -> KMSDRM panel
```

works for this frame. `glFinish()` and `SDL_GL_SetSwapInterval(1)` were also tested and did not alter the later black state.

After the controller prompt, the game switches to application FBO2. The latest KHR_debug trace reports:

```text
GUA-FBO status fb=2 status=0x8cd5
GUA-FBO status fb=2 status=0x8cdd
GUA-KHRDBG ... op=glClear/27 fb=2 ...
msg=Error:glClear::currently bound framebuffer is not valid for this operation
```

Subsequent title draws use `fb=2` and repeatedly hit the same invalid-framebuffer condition. The physical frame captured 20 seconds after swap 10 is black/fade.

## Targeted gl4es A/B

A source-level change was tested only in gl4es' `LIBGL_FBOFORCETEX` renderbuffer-to-secondary-texture path:

```text
RGBA4 renderbuffer secondary texture:
internal format = GL_RGBA
external format = GL_RGBA
pixel type      = GL_UNSIGNED_BYTE
```

Marker:

```text
GUA-GL4ES fbotex-storage tex=2 rb=2 size=1024x768 fmt=0x8058
```

All server-side FBO workarounds remained disabled. Result:

- controller prompt still renders and reaches the physical panel;
- FBO2 still transitions from `0x8cd5` to `0x8cdd`;
- KHR still reports `glClear` on invalid FBO2;
- title draws still use `fb=2`;
- physical frame after 20 seconds remains black/fade.

This targeted format change is rejected as a fix. The remaining FBO2 problem is not explained solely by the `RGBA4` secondary-texture external format.

## KHR_debug messages

KHR callback is available on the existing GLES context:

```text
GUA-KHRDBG enabled callback=... control=...
```

Relevant messages include:

```text
glGetFramebufferAttachmentParameteriv::<pname> is not valid for this attachment
glClear::currently bound framebuffer is not valid for this operation
glDrawArrays::currently bound framebuffer is not valid for this operation
glDrawElements::currently bound framebuffer is not valid for this operation
glGenerateMipmap::<level> is not an accepted value
```

The attachment-query messages are generated by diagnostic queries for renderbuffer attachments and are not treated as game errors. The repeated `glClear`/draw messages on FBO2 are generated during the game dispatch path and remain the primary blocker.

The frontend errors remain separate:

```text
SetConstants() glError (0x500)
SetConstants() glError (0x502)
```

No `GUA-GL4ES shim-set source=...` line was present in the captured logs.

## Next technical boundary

Do not add another generic FBO workaround. The evidence now requires one of:

1. capture gl4es's exact FBO2 color/depth/stencil bookkeeping at the moment it changes to `0x8cdd`;
2. compare FBO2 attachment state before and after the title transition;
3. trace the title renderer's `fb=2` creation path and identify which attachment becomes dimension-incompatible;
4. only then implement a narrowly scoped fix for that attachment.
