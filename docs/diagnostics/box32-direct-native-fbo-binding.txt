Native draw binding trace
-------------------------
A diagnostic-only native `glGetIntegerv(GL_FRAMEBUFFER_BINDING)` was added at the
entry of selected program18/program22/program86 draw calls. It does not change
framebuffer state.

At representative scene draws:

  program=18 logical_current=0 logical_draw=0 logical_read=1 native_binding=0
  program=22 logical_current=0 logical_draw=0 logical_read=1 native_binding=0
  program=86 logical_current=0 logical_draw=0 logical_read=1 native_binding=0

The trace also reports `mainfbo_fbo=0` in the pipeline events. Therefore logical
FBO0 correctly maps to native default framebuffer 0 in this runtime. There is no
observed native FBO1 draw binding around the program18/program22/program86 scene
draws.

Resolve sequence
----------------
The presentation/resolve path later changes logical state to:

  current=2, draw=2, read=1, native=2
  temporary ReadDraw_Push(GL_READ_FRAMEBUFFER) -> native=1
  FBO1/native1 source sample -> rgba=0,0,0,255
  restore -> native=2
  BLIT read=1 draw=2
  FBO2 texture2 destination sample -> rgba=0,0,0,255

This confirms a real state split:

  scene draw target: native default FBO0
  resolve read target: native FBO1

However, this is not by itself proof of a bug. FBO1 may be a game/internal
read target, or the application may intentionally draw to the default surface.
No hardcoded redirection or global FBO remapping was applied.
